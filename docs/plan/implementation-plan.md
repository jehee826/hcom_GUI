# hcom_gui 구현 계획

[요구사항과 아키텍처](../design/architecture.md)에 따른 검증 계획이다. 1단계에서 Windows의 입력·회신·최종 답변 경로를 확인한 뒤, 최우선으로 2단계 프로젝트별 세션 격리를 검증한다. 확인 결과와 다음 작업은 [인계 문서](../HANDOFF.md)에 갱신한다.

## 1. 세션 왕복 검증

**준비.** 구현 시점에 Windows에서 사용할 hcom·Codex·`agy`의 버전과 인증 상태를 확인하고 조합을 기록한다. 이 실험에는 원격 저장소와 커밋이 없는 임시 Git 레포 한 개를 사용한다. 예상 초기 브랜치 이름을 미리 지정하고, 그 브랜치의 이름만 조회한다. 커밋 전에도 브랜치 참조를 확인할 수 있는 `git symbolic-ref --short HEAD`를 기준값 확보에 사용한다. [Git symbolic-ref 문서](https://git-scm.com/docs/git-symbolic-ref)

**1A · Codex 직접 왕복.** 빈 레포를 작업 경로로 지정한 App Server에 한 개의 스레드를 만든다. 앱 입력을 재현하는 검증 클라이언트에서 “현재 브랜치 이름만 답해”를 보낸다. `threadId`, 요청과 연결된 `turnId`, `item/completed`의 본문과 `phase`, `turn/completed` 상태를 기록한다. 클라이언트를 다시 연결하고 저장 ID로 재개해 같은 조회를 한 번 더 수행한다.

**통과 기준.** 두 번 모두 같은 `threadId`에 서로 다른 `turnId`로 접수되고, 성공 종료와 함께 사전 지정한 브랜치 이름이 최종 본문에 일치한다. 중간 메시지와 완료 본문을 구분한다. 턴이 완료돼도 최종 본문이 확인되지 않은 경우 성공으로 집계하지 않는다.

**1B · hcom 경유 왕복.** 동일한 테스트 레포에서 Codex의 수동 hcom 참가자를 스레드에 연결하고 `agy` 워커를 같은 `HCOM_DIR`으로 띄운다. 저장한 `threadId`에 “Antigravity에 현재 브랜치 이름 조회만 맡기고 확인해 줘”를 보낸다. Codex의 위임 도구 호출을 hcom의 작업 이벤트에 연결한다. 동일 이벤트를 참조한 `agy` 결과를 같은 Codex 스레드에 도구 결과로 입력하고, 검토 턴의 최종 본문을 기록한다. CLI 버전, 프로세스·참가자·세션 ID, 요청·회신 이벤트 ID와 턴 ID를 대조한다.

**통과 기준.** Codex와 `agy` 참가자가 각각 하나이고, 다음 증거가 순서대로 남는다. ① Codex 위임 도구 호출 ② 지정된 `agy`로의 hcom 전송 ③ 올바른 발신자와 원본 이벤트를 참조한 실제 `agy` 회신 ④ 동일 `threadId`의 검토 턴 ⑤ 성공 종료와 예상 브랜치명 최종 본문 1개. 첫 조회와 위임 조회 모두 프로젝트 파일, HEAD 참조, 커밋 이력을 바꾸지 않는다. hcom 전송만 확인된 경우는 미통과다.

**연결 복구 통과 기준.** 회신을 받는 이벤트 구독을 끊었다 다시 연결해 저장한 커서 이후의 회신을 한 번만 처리한다. 같은 `requestId` 또는 hcom 이벤트가 재등장해도 중복 요청·검토 턴을 만들지 않는다. `agy`를 정상 중지한 뒤 저장된 conversation ID로 재개해 같은 대화임을 확인한다. 승인 대기에서 성공 상태를 내보내지 않고 로컬 조치 경로를 확인한다.

**경로 결정.** 두 왕복과 ID 복구를 통과하면 해당 버전을 고정한다. App Server 단독 왕복은 통과했으나 수동 참가자 연결·동적 도구·회신 주입이 막히면 `hcom codex` 관리형 경로와 Codex `notify`를 같은 브랜치 조회로 검증한다. 이 대안은 hcom 수신자와 Codex `thread-id`의 고정 매핑, 요청별 식별자와 `notify`의 `input-messages` 대응, hcom 회신과 사용자 요청·중간 턴의 구분, 최종 `turn-id`·본문을 모두 확인할 수 있을 때만 채택한다. 어느 경로도 같은 세션의 최종 응답을 안정적으로 식별하지 못하면 2단계에 연결하기 전에 통합 설계를 수정한다.

## 2. 프로젝트 선택과 격리

**작업.** 프로젝트 등록·목록·선택, Git 공용 디렉터리 기반 중복 등록 검사, 프로젝트별 `HCOM_DIR`, Codex와 워커별 작업 디렉터리·대화 ID 저장, 시작·재개 잠금, hcom 상태 수집과 인계 기록을 구현한다. 기본 워커 등록과 추가 워커 생성·개별 재개를 백엔드에 연결하고, 화면은 3단계에서 붙인다.

**통과 기준.**

- A·B를 동시에 시작한다. 각 프로젝트의 `HCOM_DIR`, Codex `threadId`, 기본 `agy` conversation ID가 서로 다르다. 각 hcom 목록과 Codex 워커 조회에는 자기 프로젝트 참가자만 보인다. 양방향으로 상대 프로젝트 `workerId`를 지정하거나 상대 프로젝트에 이미 귀속된 대화 ID를 재사용하려 하면 거절되고 상대에게 메시지·작업 기록이 추가되지 않는다.
- A에 워커를 하나 추가한다. A의 기존 Codex와 기본 `agy` ID는 유지되고, 추가 워커는 별도 `workerId`, conversation ID, hcom 참가자 ID를 받는다. A에는 참가자가 셋, B에는 둘이다. 같은 추가 요청을 재전송해도 참가자가 늘어나지 않으며, 선택한 A 워커 한 곳만 작업을 수신한다.
- A에 연결된 기존 worktree를 선택하면 저장한 A의 `projectId`와 `HCOM_DIR`을 유지한다. 재개 후 이동한 세션의 기존 대화 ID와 실제 `cwd`를 확인한다. B의 작업 경로를 A의 세션에 지정하려는 요청은 거절된다.
- 데스크톱 이중 클릭이나 두 클라이언트의 동시 시작 요청에도 프로젝트마다 활성 Codex 하나와 워커마다 활성 세션 하나를 유지한다. 추가 워커를 중지하고 개별 재개하면 저장한 ID를 사용한다. 창 닫기와 프로젝트 전환 전후로 ID가 동일하다. 백엔드를 다시 열면 저장된 ID와 살아 있는 프로세스를 대조한 뒤 재연결 또는 재개한다.
- 목표·설계 문서·브랜치/커밋·테스트 결과·다음 작업이 A 또는 B의 인계 기록에만 남는다. 값이 없는 항목은 `미실행`, `커밋 없음`, `확인 필요` 등 의미에 맞는 상태로 조회된다.

## 3. 지시 화면

**작업.** 왼쪽 프로젝트 사이드바, 가운데 Codex 대화·하단 지시창, 오른쪽 워커·인계 패널을 공통 화면에 구현한다. 워커 패널에 워커별 상태와 `워커 추가`, 시작·재개를 연결한다. HTTP 전송은 `projectId`와 `requestId`를 사용한다. SSE는 프로젝트별 기록과 커서를 사용하며 끊긴 동안 저장한 결과를 재생한다. Electron 창을 닫아도 트레이 백엔드가 유지된다.

**통과 기준.**

- 데스크톱에서 사이드바로 프로젝트를 전환하고 하단 지시창으로 요청을 보낸다. 워커 패널의 `워커 추가`는 누를 때 선택한 프로젝트에 적용된다. 처리 도중 다른 프로젝트로 전환해도 새 워커와 그 상태는 원래 프로젝트에만 표시된다.
- 선택된 A에 의도적으로 위임이 필요한 지시를 넣으면 `접수 → Codex 실행 → 워커 작업 중 → Codex 검토 → 완료`를 확인한다. Codex의 직접 응답, 실패, 중단, 승인 대기, 최종 본문 누락을 성공과 구분한다. 답변은 해당 프로젝트에 한 번만 남는다.
- A 작업 중 B로 전환하면 늦게 도착한 A 이벤트가 B 화면과 기록에 추가되지 않는다. A로 돌아오면 같은 세션의 진행 상태와 결과를 확인한다. A 요청을 전송한 창을 닫고 다시 열어도 같은 결과를 보며, 요청이 중복 실행되지 않는다.
- 전송 직후 연결이 끊긴 경우 같은 `requestId` 재조회로 원래 요청을 확인한다. 접수 여부를 복원하지 못한 건은 `확인 필요`로 남긴다. 폴더 등록·지시 전송 권한을 확인하고, 답변과 로그는 브라우저에서 실행 가능한 HTML로 해석되지 않도록 렌더링한다.

## 4. 폰 접속과 최종 검증

**작업.** Windows 루프백 서버에 Tailscale Serve를 연결한다. 승인된 폰만 접속하는 사설망 정책과 HTTPS, 일회용 페어링과 앱 세션을 적용한다. 폰 화면은 데스크톱과 동일한 자산·API·이벤트 기록을 사용한다. [Tailscale Serve](https://tailscale.com/docs/features/tailscale-serve) · [Tailscale 접근 정책](https://tailscale.com/docs/features/access-control/grants)

**통과 기준.**

1. A·B를 모두 실행하고 A에 추가 워커 하나를 시작한다. 각 프로젝트의 `HCOM_DIR`, Codex `threadId`, 워커별 `workerId`와 conversation ID, 참가자 ID를 적어 둔다. 프로젝트마다 서로 다른 브랜치명을 사용한다.
2. 인증된 폰의 프로젝트 메뉴에서 A를 고른다. 워커 패널에는 A의 기본·추가 워커만 보인다. 지시창에서 A의 추가 워커에게 브랜치명 조회를 위임하라고 요청한다. 지정된 워커만 회신하고 A의 Codex 검토 턴만 최종 답변을 낸다. A 데스크톱과 A 폰에는 동일한 결과가 한 번씩 표시되고 B의 상태·메시지·인계 기록에 A 요청의 흔적이 없다.
3. A 진행 중 폰 연결을 끊고 재접속한다. 모든 세션 ID가 유지되고 커서 이후의 상태와 최종 답변을 한 번만 받는다. 후속 지시도 A의 같은 Codex와 지정 워커 세션에 도착한다. 재접속 전후 활성 세션 수는 A가 Codex 하나와 워커 둘, B가 Codex 하나와 워커 하나다.
4. 앱 인증이 없는 브라우저는 API·이벤트 스트림을 읽거나 지시를 보낼 수 없다. 승인된 사설망 밖의 기기와 정책상 제외한 tailnet 기기에서 접속할 수 없다. 사설 Serve URL과 정책을 확인하고, LAN 직접 접속·공개 접속 경로가 열려 있지 않은지 확인한다.

**완료 기록.** 검증 조합의 버전, 단계별 통과 근거, 세션·턴과 hcom 이벤트의 대응 관계, 재접속 전후 ID, A·B의 결과를 남긴다.

## 5. Windows 설치와 릴리즈

**작업.** Windows x64 설치형 `.exe`를 만들고 `hcom`, `agy`, Codex의 실행 파일과 로그인 상태를 설치 후 점검한다. Windows의 hcom 워커 훅이 영속 사용자 `PATH`에서 실행 파일을 찾는 조건을 확인한다. 기본 브랜치는 `main`으로 두고 GitHub Actions에서 버전과 Windows 설치 파일을 검증한다. 개발 변경은 기능 브랜치에 모으고, 사용자가 버전 완료를 정하면 `1.0.0`, `1.1.0`, `1.2.0` 순의 버전 브랜치에서 `main`으로 PR을 연다. 버전 PR이 병합되면 설치 파일을 빌드해 릴리즈에 올린다. [HTMLViewer 릴리즈 워크플로](https://github.com/jehee826/HTMLViewer/blob/main/.github/workflows/release.yml)

**통과 기준.** Windows에서 `.exe` 설치 후 시작 메뉴로 앱을 열 수 있다. 처음 실행 시 CLI별 설정 필요 여부가 표시되고, 등록한 프로젝트와 대화 ID가 업데이트 후에도 유지된다. 버전 브랜치 이름, 앱 버전, 릴리즈 태그가 일치하며 릴리즈에 다운로드 가능한 설치 파일이 첨부된다. 첫 릴리즈는 사용자의 버전 완료 지시 뒤에 진행한다.
